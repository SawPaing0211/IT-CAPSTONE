## Subjects, enrollment and historical access

**Code:** `Subject` owns curriculum metadata and supported languages. `SubjectSection` owns its subject, class code, schedule/room, capacity and semester/academic-year labels. `TeacherAssignment` links instructor, subject and section. `IrregularEnrollment` is the actual membership table for **both** regular and irregular imports; there is no student academic-year field in `User` and no separate persisted student-type field. “Blocks” are obsolete; use subject/class identities.

Administrators create catalog/class entries, assign teachers, then enroll students manually or through CSV. Master enrollment requires `student_id, firstname, lastname, student_type, section_no`; middle name/suffix are optional and legacy year-level columns are ignored. A separate user-only CSV path has different validation, including a 7–10 digit student-ID rule. IDs are strings. Repeated membership is skipped; imports can partially succeed and return row errors plus credentials for new accounts. Credential files require controlled delivery. Capacity is metadata, not an observed enforced enrollment ceiling; `current_count` is a cache and some reads derive actual membership counts.

First-year metadata guards stop new catalog/enrollment/content activity for other or unclassified curriculum years. Existing records remain. The legacy 16-entry seed array still contains second-year entries; new seeding selects only its **eight** year-one entries. This is **not** an approved institutional catalog: it even includes Data Structure & Algorithm. Subject creation accepts new codes rather than enforcing a confirmed official allowlist. Do not treat the seed array or a year-one label as curricular approval.

Student quest access is section-based, requires publication, and hides hidden-case values. Formerly enrolled students with a stored submission can retain read access to that published quest, their drafts/hints and own results; historical access does **not** authorize new Run/Submit/hint actions. Lesson-file access requires current enrollment and publication; do not promise universal former-student materials access. Unpublishing/deleting a quest can affect historical access. Section deletion can cascade to lessons, announcements, quests and submissions; student deletion also removes related records. A retention policy and deletion safety need review before real data.

## Run, drafts, final Submit and rewards

**Owner:** unlimited ungraded practice, one confirmed final graded Submit, infrastructure failures never consume it; server drafts, submitted-code read-only and authorization must survive the redesign.

**Code:** Run is synchronous and rate-limited (20/minute at the quest route); “unlimited” means no graded-attempt quota, not unrestricted request throughput. It saves no submission/XP and can run after a deadline/submission while currently authorized. All defined cases are evaluated but hidden inputs/outputs are redacted. The separate sandbox has its own endpoint and limits. Drafts persist per user/quest/language on the server, with a user-scoped localStorage cache in the current editor. Autosave errors currently go to the console, so the approved explicit save/error/retry UX is still a connected-design deliverable. Submitted drafts reject writes; the UI editor becomes read-only. Deadline expiry alone does not make the current editor read-only.

Submit checks role, published visibility and deadline, claims a unique user/problem reservation, then runs code without holding a database transaction. A pending reservation blocks duplicates; after 15 minutes one worker can take over. Owner tokens prevent late workers from finalizing/releasing someone else's slot. Final submission, slot completion, additive XP and level update commit together, with bounded retries for MySQL lock failures. Runner/save failures release the attempt; loss of the success response requires checking saved state rather than submitting again. More than 15 minutes of legitimate grading is an unresolved operational risk.

Observed scoring: accepted = full quest XP; partial = passed-case ratio × partial-credit percentage with a floor; wrong/error/timeout = `max(5, 10% of quest XP)`; revealed hint penalties subtract once, floored at zero. No cases produces error/zero. Level = `1 + XP // 100`. Difficulty XP ceilings are 100/250/500. These are gamification values, **not academic grades or validated proficiency**. Timeout participation credit remains an owner policy question from earlier reports. Event quests use normal scoring, not a bonus multiplier. Debugging is a quest type/starter-code workflow, not a separately implemented timed game. Stored `auto_grade`, prerequisites and estimated time do not establish a manual grading queue, unlock enforcement or speed-based rewards.

Deadlines are checked before execution, strictly after the due instant. API parsing normalizes UTC; UI displays Asia/Manila. The current instructor builder has no deadline control; empty/null update does not clear an existing deadline. See [quest states](C:/Users/Christian/forge-dev/docs/QUEST_STATES.md), [Submit implementation](C:/Users/Christian/forge-dev/backend/app.py:2153), [editor](C:/Users/Christian/forge-dev/frontend/src/pages/Student/StudentCodeEditor.jsx:254), [grading/recovery tests](C:/Users/Christian/forge-dev/backend/tests/test_grading_and_recovery.py), [deadline tests](C:/Users/Christian/forge-dev/backend/tests/test_score_and_deadline.py).

## Architecture, services and operations

**Code:** React 19, React Router 7, Vite 8, Tailwind 3 and locally bundled Monaco form the browser client. Flask 3, JWT-Extended, SQLAlchemy/PyMySQL and Werkzeug serve the API; most models/routes live in `backend/app.py`. MySQL 8.0 is the Compose target; SQLite supports isolated tests/demo. Submission grading runs per test case through Docker Python/Java/C# sandbox images. There is no inspected background queue/worker or WebSocket pipeline; React fetch/refresh and synchronous requests provide updates.

Docker limits are Python 10s/128MB, Java 15s/256MB, C# 60s/512MB; common 0.5 CPU, 64 processes, no network, dropped capabilities and output/code limits. Limits and actual backend-to-host Docker socket/matching scratch-path topology require deployment validation; sandbox presence alone is not a security certification. Planned hosting is Vercel frontend plus Linux VPS backend/MySQL behind Nginx/TLS, not a verified deployed environment.

Manual token-set Jaccard scans compare latest submissions per student for a quest. Optional Google GenAI calls request plain-language explanations for up to ten flagged pairs; without configuration/service availability, similarity still works. The code sends student names and code previews to that external API when enabled; client-approved data handling and service validation are outstanding before real-data use. Model/quota claims in comments were not verified. There is no AI code authoring or AI grading. Scan responses are not proof of a persisted moderation workflow. Admin audit logging is not comprehensive learner-event tracking.

State comprises database rows **and lesson attachments** in the uploads volume. SQL-only admin backup excludes files. The full-backup tool records SQL, uploads and hashes; secrets, certificates and hosting settings require separate recovery arrangements. Existing restore rehearsal is supplied synthetic evidence, not real-copy or full deployment-volume recovery. New award uniqueness also affects restoring older duplicate-bearing backups. Startup checks schema; it does not automatically migrate a normal/production database. Explicit upgrades may partially apply additive DDL before detecting blocked award uniqueness.
